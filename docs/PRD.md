## 1. 项目概述

### 1.1 项目背景

当前测试过程中，日志查询、数据库查询、Redis 查询、接口测试、性能测试等操作分散在不同工具中，缺乏统一入口，存在以下痛点：

- 日志查询需要登录服务器或在多个日志平台间切换，效率低
- 数据库 / Redis 查询依赖 Navicat、Redis Desktop Manager 等桌面工具，权限分散、操作不可审计
- 接口测试用例分散在 Postman、JMeter 等工具中，团队间难以共享和沉淀
- 缺乏统一的工具集，日常测试辅助功能（如 JSON 格式化、加解密、时间戳转换等）散落各处

### 1.2 项目目标

构建一个**一站式 Web 测试平台**，将常用测试能力统一收口，实现：

1. 集中查询：日志、数据库、Redis 在同一个平台内完成查询
2. 统一测试：接口测试、性能测试在同一平台内配置、执行、查看报告
3. 工具集成：常用测试辅助工具统一集成在"工具菜单"中
4. 权限管控：按角色控制各功能模块的访问与操作权限

### 1.3 目标用户

| 角色 | 说明 | 核心诉求 |
|:-----|:-----|:---------|
| 测试人员 | 平台主要使用者 | 快速查日志/查库/查缓存、执行接口与性能测试 |
| 开发人员 | 协助定位问题 | 查日志、查数据库定位缺陷 |
| 运维人员 | 环境与数据源维护 | 管理数据源连接、监控平台运行 |
| 平台管理员 | 系统管理 | 用户/角色/权限管理、数据源配置、审计日志 |

| API-10 | 质量门禁 | CI 触发执行时可设置通过率/失败用例数阈值，作为流水线质量门禁，未达标返回失败状态 | P1 |
| API-11 | 结果回传 | 执行完成后将结果（通过/失败、报告链接）回传 CI 流水线，支持在构建详情中查看测试报告 | P1 |
| API-12 | OpenAPI 导入 | 从 OpenAPI 2.0/3.0（Swagger）文档一键导入生成接口用例，自动解析请求参数与数据结构 | P0 |
| API-13 | 前后置脚本 | 支持 Pre-request 脚本与后置处理脚本（JS），实现签名计算、动态参数、响应数据处理 | P1 |

**API-08 与 CI 集成（API-09~11）的关系说明**：

| 维度 | API-08 平台内定时任务 | API-09~11 CI 持续集成 |
|:-----|:---------------------|:----------------------|
| 触发方 | 平台自身调度器（cron） | 外部 CI 流水线（Jenkins/GitLab 等） |
| 触发时机 | 固定时间点（如每晚 22:00 回归） | 代码事件（提交、合并请求、构建完成） |
| 使用场景 | 常态化巡检、无人值守回归 | 版本发布门禁、提交前快速验证 |
| 结果去向 | 通知中心 + 测试报告中心 | 回传 CI 作为质量门禁 + 测试报告中心 |
| 执行引擎 | 同一套用例执行引擎 | 同一套用例执行引擎 |

两者**共用同一用例库与执行引擎**，仅触发与结果消费方式不同；同一用例集合可同时被定时任务与 CI 流水线引用，互不冲突。CI 触发产生的执行记录通过 SCH-09 与构建号/提交号关联。

## 3. 非功能需求

### 3.1 性能需求

- 普通页面（列表、编辑）首屏响应时间 ≤ 2s
- 日志检索、SQL 查询结果加载在合理数据量下 ≤ 5s（大结果集异步分页加载）
- 压测执行期间，平台自身监控数据刷新延迟 ≤ 3s

### 3.2 安全需求

- 数据源账号密码、环境变量中的敏感信息**加密存储**，禁止明文入库
- 所有查询/执行类操作遵循最小权限原则
- 数据库、Redis 默认**只读**，写操作需角色授权 + 二次确认
- 平台自身登录需鉴权，敏感接口防越权访问
- SQL 注入防护（平台自身接口参数校验）
- 操作审计日志不可被普通用户删除

### 3.3 可用性需求

- 核心功能（日志查询、数据库查询、接口测试）需稳定运行，故障可快速恢复
- 关键操作有操作提示与错误反馈，不出现"无响应"状态

### 3.4 可维护性需求

- 模块化架构，各功能模块可独立开发、独立部署（或插件化扩展）
- 数据源配置统一管理，支持批量导入导出
- 提供平台运行日志，便于排查平台自身问题

## 5. 接口用例 CI 集成对接说明

> 本章为设计参考，接口路径、参数名均为示意，实际以开发设计文档为准。

### 5.1 平台侧准备（一次配置）

1. 在"任务调度"模块创建 CI 触发配置：选择用例集合、执行环境、质量门禁阈值（如通过率 ≥ 98%）
2. 生成该配置的 **CI Token**（可吊销、可设置有效期），并在"触发认证"中配置允许来源
3. 获取执行 API 地址，形如 `POST /api/v1/ci/executions`，参数示例：

```json
{
  "config_id": "ci_8f3a2b",       // CI 触发配置 ID
  "build_no": "20260920.1",       // 构建号（回传用）
  "commit_sha": "a1b2c3d4",       // 提交号（回传用）
  "trigger_source": "jenkins"
}
```

### 5.2 Jenkins 对接示例

```groovy
// Jenkinsfile 片段：构建完成后执行接口用例回归
pipeline {
    agent any
    environment {
        CI_TOKEN = credentials('test-platform-ci-token')  // 平台生成的 CI Token
        PLATFORM_URL = 'http://test-platform.example.com'
    }
    stages {
        stage('Build') { steps { /* 原有构建步骤 */ } }
        stage('API Regression') {
            steps {
                script {
                    def resp = sh(script: """
                        curl -s -X POST '${PLATFORM_URL}/api/v1/ci/executions' \
                          -H 'Authorization: Bearer ${CI_TOKEN}' \
                          -H 'Content-Type: application/json' \
                          -d '{"config_id":"ci_8f3a2b","build_no":"${BUILD_NUMBER}","commit_sha":"${GIT_COMMIT}","trigger_source":"jenkins"}'
                    """, returnStdout: true).trim()
                    def result = readJSON text: resp
                    // 质量门禁：平台返回 passed/failed，failed 则流水线失败
                    if (result.status != 'passed') {
                        error "接口用例回归未通过：${result.report_url}"
                    }
                    echo "接口回归通过，报告：${result.report_url}"
                }
            }
        }
    }
}
```

### 5.3 GitLab CI 对接示例

```yaml
# .gitlab-ci.yml 片段
stages:
  - build
  - test

api-regression:
  stage: test
  only:
    - merge_requests   # 合并请求时触发
    - tags             # 打标签（发版）时触发
  variables:
    PLATFORM_URL: "http://test-platform.example.com"
  script:
    # 通过率低于阈值时平台返回非 0 退出码，流水线自动失败
    - curl -s -X POST "${PLATFORM_URL}/api/v1/ci/executions"
        -H "Authorization: Bearer ${TEST_PLATFORM_CI_TOKEN}"
        -H "Content-Type: application/json"
        -d "{\"config_id\":\"ci_8f3a2b\",\"build_no\":\"${CI_PIPELINE_ID}\",\"commit_sha\":\"${CI_COMMIT_SHA}\",\"trigger_source\":\"gitlab\"}"
```

### 5.4 质量门禁判定规则

| 返回码 | 含义 | 流水线处理 |
|:------|:-----|:-----------|
| 0（passed） | 执行完成且通过率达标 | 继续后续阶段 |
| 1（failed） | 执行完成但未达门禁（通过率不足/失败用例超限） | 流水线失败，阻断发布 |
| 2（error） | 执行异常（环境不可用、超时、配置错误） | 流水线失败，需人工排查 |

> 说明：CI 触发、平台内定时、手工执行**共用同一用例库与执行引擎**；CI 执行记录通过 SCH-09 关联构建号/提交号，可在"任务调度 → 执行历史"和"测试报告中心"追溯。

## 7. 待确认问题

1. **技术栈**：前端/后端采用什么技术栈？是否有团队既有技术偏好？
2. **日志来源**：当前日志存在哪里（ELK？Loki？云服务？还是服务器文件）？是否需要对接多套？
3. **数据库范围**：需要支持哪些数据库类型？是否已有统一的数据访问网关？
4. **Redis 规模**：连接的是单机还是集群？是否跨环境（dev/test/prod）都要接入？
5. **接口测试**：现有 Postman 用例是否需要迁移导入？用例管理是否需要与现有用例管理平台（如禅道 / Xray）同步？
6. **性能测试规模**：压测最大并发目标是多少？是否需要分布式压测？
7. **部署形态**：平台部署在公司内网还是云上？是否需要对接企业统一登录（SSO）？
8. **用户规模**：预计使用人数、是否需要多租户隔离？
9. **通知渠道**：邮件 / 钉钉 / 企微具体用哪些？是否有现成的机器人 Webhook 可用？
10. **缺陷系统**：使用禅道还是 Jira？是否已有可用的 API 凭据？
11. **Mock 需求**：Mock 服务是否需要支持脚本动态逻辑，还是静态返回即可？
12. **审批流**：高危操作审批是否必须？审批人角色如何设定？
13. **CI 平台**：持续集成对接 Jenkins / GitLab CI / GitHub Actions 中的哪个？质量门禁（通过率阈值）由谁定义？
14. **多项目空间**：平台是否需要按项目隔离（多产品线）？还是单团队共用一套即可？
15. **配置中心**：是否需要对接 Nacos / Consul 等配置中心自动获取服务地址？
